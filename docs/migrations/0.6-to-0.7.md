# Migrating from risaml `0.6` to `0.7`

Update the dependency to `risaml = "0.7"` and refresh the consumer lockfile.
This release uses ribergshamra 0.11 on riptering 0.7 and ritsp-ltv 0.6.
Applications that also name these dependencies directly must select matching
release lines: their exported types are distinct from the older versions.
The MSRV remains Rust 1.88. Existing provider feature names and the
`crypto-bergshamra` compatibility alias remain available.

## Software RSA decryption

RustCrypto RSA key-transport decryption is disabled in the backend by default.
The existing runtime software-RSA risk option alone can no longer enable it.
Applications that deliberately retain that compatibility exception must enable
`crypto-legacy-rsa-decryption` and explicitly select the existing
`XmlEncryptionPolicy` software-RSA risk option, or its raw API equivalent.
Neither the default features nor `crypto-legacy-algorithms` enable the exception.
It accepts the unresolved RUSTSEC-2023-0071 timing risk; it does not fix it.
RSA signing, verification and encryption are unchanged. AWS-LC and FIPS retain
their provider-specific algorithm restrictions.

## XML processing and token keys

The delegated XML backend applies fixed input, DOM, expression, transform and
output budgets. Canonicalization corrections can change the bytes covered by a
signature, and CRL validation accepts only the supported authenticated,
current, complete/direct profile. Review the
[XML processing limits and migration policy](https://github.com/Rhein-Industries/ribergshamra/blob/v0.11.0/docs/security-limits.md)
before upgrading deployments that relied on larger inputs or older behavior.

PKCS#11 operation admission now requires readable, unique key-type and
parameter attributes matching the requested operation. RSA token keys must be
at least 2048 bits. Tokens that hide required parameters fail closed; expose
the required public attributes and replace undersized RSA token keys. This is
separate from the historical software RustCrypto key-size policy.

## Validation and metadata

Unknown assertion Conditions, unsupported reference transforms, signature
positions outside the message/metadata root or direct Response assertion, and
signature `ds:Object` content now fail closed. Same-document reference preflight
also covers nested signatures. Inputs accepted because these checks were absent
must be corrected at the producer; no general validation bypass is provided.

Metadata `validUntil` is enforced at use after import. Refresh expired metadata,
keep SP and IdP role imports distinct, and supply keys with the appropriate
signing or encryption purpose. `OneTimeUse` assertions require replay storage
in typed processing.

Typed pending SSO and SP-initiated SLO correlation expires after five minutes by
default. Use `StartSso::pending_lifetime` or `StartSlo::pending_lifetime` to set
an explicit local lifetime when needed. Restored pending requests using replay
cache enforcement must carry an expiration; retain completed request IDs in the
cache. IdP-initiated SLO retains its generated wire deadline unless explicitly
shortened.

Malformed XML, incomplete raw-DEFLATE streams, malformed certificates and
unrepresentable clock-skew bounds now return validation errors. Custom
AES-192-CBC Response encryption follows the existing CBC integrity policy.
Wire namespaces and protocol constants remain unchanged. See the
[changelog](../../CHANGELOG.md) for the complete release changes.
